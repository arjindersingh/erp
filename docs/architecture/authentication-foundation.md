# Authentication Foundation

## Requirement Review

The ERP uses one shared database and one global login namespace. Authentication
starts only after the request domain resolves a tenant. A global `User` may be
associated with one tenant-owned `Person` in each tenant, and that Person may
have several Profiles and scoped Memberships.

The security boundary is the active tenant Membership. A role, profile, portal,
or visible menu item does not establish tenant access by itself.

## Final Architecture

```text
Platform
├── User (global authentication principal)
│   ├── user_person_links ───────────────┐
│   ├── user_memberships                 │
│   └── role_assignments                 │
│                                        │
└── Tenant                               │
    ├── Person (tenant-owned human) <────┘
    │   ├── person_contacts (many email/mobile/WhatsApp values)
    │   └── Profiles (teacher, guardian, student, employee, ...)
    └── Access Scopes
        ├── Company
        ├── Campus
        └── Institute

UserMembership
├── Tenant
├── User
├── Person/Profile (nullable for service accounts)
├── AccessScope
└── RoleAssignments ──> Spatie Role ──> Permissions
```

Concept ownership:

| Concept | Responsibility |
| --- | --- |
| `User` | Global credentials, verification, status, lock and password state |
| `Person` | Tenant-owned human and human-facing identity data |
| `Profile` | Persona such as teacher, guardian, student, employee, or alumni |
| `UserPersonLink` | Connects one global account to the tenant's Person record |
| `UserMembership` | Grants tenant and organisational association for a profile |
| `AccessScope` | Reusable tenant/company/campus/institute boundary; contains no role |
| `RoleAssignment` | Assigns a Spatie role to one Membership for a bounded period |
| `Portal` | Authentication UI context; added in the portal-selection milestone |

Direct Spatie roles on `User` are reserved for platform-wide identities such as
site administrators. Tenant role checks will resolve through active Memberships
and RoleAssignments; calling `$user->can()` alone is not sufficient for a tenant
command until the scoped authorization resolver is installed.

## Database Decisions

- Login email is globally unique. Optional username and mobile are also globally unique.
- `users.password` is nullable for pending invitation accounts; only an active account with a valid hash may authenticate.
- Public UUIDs are generated by models while integer keys remain efficient internal joins.
- Person contact values are normalized in `person_contacts`; `primary_email` and `primary_mobile` are display/search projections, not login credentials.
- Composite foreign keys prevent memberships from combining records from different tenants.
- Global tenant scopes are not enabled. Explicit `forTenant()` queries, policies, middleware, and composite constraints avoid hidden behavior in queues and platform administration.
- Soft deletes are used for Users, Persons, and Profiles. Memberships and assignments retain status and date history instead of being soft deleted.

## Migration Order

Authentication-relevant migrations execute in this order:

1. `0001_01_01_000000_create_users_table.php`: users, reset tokens, base database sessions.
2. `2026_08_03_054843_create_permission_tables.php`: Spatie roles and permissions.
3. `2026_08_03_060548_create_personal_access_tokens_table.php`: Sanctum tokens.
4. `2026_08_03_071000_create_tenant_organization_tables.php`: tenants, hierarchy, domains, reusable access scopes.
5. `2026_08_03_072000_create_person_user_identity_tables.php`: persons, contacts, profiles, account links, memberships, role assignments.

Login history, tenant-aware session extensions, invitations, two-factor records,
trusted devices, portal definitions, and portal assignments get additive migrations
in their owning milestones.

## Framework and Packages

Already installed and selected:

- Laravel authentication contracts, password broker, hashing, signed URLs, verification, rate limiting, sessions, CSRF, notifications, and events.
- Laravel Sanctum for first-party API tokens and abilities.
- Spatie Laravel Permission for role and permission definitions.
- Spatie Activitylog for business audit records; security login history remains a dedicated table.
- Livewire and Tailwind for shared tenant-branded authentication UI.
- Pest/PHPUnit, Larastan, and Dusk for automated verification.

Filament is not currently installed. It will be installed and connected to the
common `User` and membership authorization layer during the Filament milestone;
no Filament-only user table will be introduced.

Redis will back cache, queues, rate limits, and optional session storage in deployed
environments. Database sessions remain supported for tenant-aware session inventory.

## Security Risks and Controls

| Risk | Foundation control | Remaining milestone work |
| --- | --- | --- |
| Cross-tenant references | Composite tenant foreign keys and `forTenant()` scopes | Policies and membership middleware |
| Login through another tenant | Membership is separate from credentials | Enforce resolved-tenant membership after credential verification |
| User enumeration | Global identifiers are not exposed by relationships | Neutral responses and layered rate limits |
| Role used outside its scope | Roles attach to Memberships, not reusable AccessScopes | Scoped permission resolver and policies |
| Inactive tenant/account | Controlled status enums | Ordered status middleware and login action |
| Invitation account takeover | Pending accounts may have no password | Hashed single-use expiring invitation tokens |
| Session theft/fixation | Laravel session infrastructure | Regeneration, tenant context binding, revocation inventory |
| Site-admin bypass misuse | Separate account type and no implicit tenant membership | Explicit privileged policies and audit logging |
| PII leakage | Tenant-owned Persons and contacts | Authorization, encryption classification, retention policy |
| UUID treated as authorization | UUID is only a public identifier | Every lookup still requires tenant policy checks |

Menu visibility will never be treated as authorization. Controllers, Livewire
actions, Filament panels, and API endpoints must independently enforce the same
active Membership, Scope, Portal, and Permission context.
